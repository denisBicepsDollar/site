# План: наблюдаемость инфраструктуры zelenyeusy.ru
### Цель — сразу видеть, ГДЕ авария, и получать alert, ЧТО она произошла

---

## 1. Что мы хотим получить (цель и критерии готовности)

**Цель:** в любой момент за 30–60 секунд ответить на три вопроса:
1. Что сломалось? (какой именно сервис: api, worker, db, nginx, сам сервер)
2. Чем это проявляется? (упал процесс, не отвечает, отвечает ошибками, завис)
3. Что с этим делать? (подсказка прямо в тексте алерта)

**Готово, когда:**
- Понятно, что именно падало — в дашборде и логах видно имя сервиса и причину, а алерт содержит название упавшего сервиса.
- Падение сервиса видно в логах/мониторинге — остановка/зависание любого контейнера отражается цветом на дашборде и уходит уведомлением в Telegram в течение 1–2 минут, даже если я в этот момент никуда не смотрю.
- Логи ошибок читаемы: у каждой ошибки есть время, сервис, уровень, стек и контекст запроса (какой URL, какой пользователь, какой request id).

**Инвентарь того, что будем наблюдать (по текущему docker-compose):**

| Компонент | Что это | Типовые аварии |
|---|---|---|
| nginx | входная точка, статика магазина + админки, прокси на api | упал процесс, 502/504 (api недоступен), забитые сертификаты |
| api | Express-сервер (порт 3000) | падение процесса, ошибки БД, необработанные исключения, зависание |
| worker | фоновый обработчик отчётов | тихо умер, «висит», но ничего не делает; циклится на одной задаче |
| db (PostgreSQL) | три базы: каталог, отчёты, пользователи | забитый диск, слишком много соединений, медленные запросы |
| certbot | продление SSL | сертификат истёк — сайт «лежит» для посетителей |
| сам VPS | хост под всем этим | кончилось место на диске (убивает Postgres), кончилась память, OOM-killer |
| снаружи | домен zelenyeusy.ru из интернета | весь сервер лежит, DNS, истёкший сертификат |

## 2. Уровень 1 — Понятное логирование ошибок

**Принцип: лог — это данные, а не эссе. Одна строка = одно событие, машиночитаемо.**

### 2.1. Единый формат для всех сервисов
- Все сервисы (api, worker) пишут логи **в stdout** в структурированном виде (JSON), а не «красивым текстом». Docker сам подхватит stdout — не нужно управлять файлами логов руками.
- Каждая строка лога содержит минимум: `время (UTC)`, `уровень (error/warn/info/debug)`, `имя сервиса`, `короткое человекочитаемое сообщение`, `контекст`.
- Инструмент: готовая библиотека структурных логов для Node (например pino или winston) — в api и worker один и тот же формат.

### 2.2. Правила уровней
- **error** — произошла авария или часть функциональности не работает: необработанная ошибка, недоступна БД, запрос упал с 5xx. Обязательно со стеком ошибки.
- **warn** — работает, но что-то не так: повторная попытка, медленный запрос, устаревший токен, упавшая задача воркера с ретраем.
- **info** — старт/остановка сервиса, приём запроса (в сжатом виде), результат фоновых задач.
- **debug** — только для расследования, в продакшене по умолчанию выключен.

### 2.3. Что пишем про каждую ошибку (обязательный контекст)
- Стек ошибки (stack trace) — чтобы видеть файл и строку, где упало.
- Для HTTP-запроса: метод, путь, HTTP-статус, request id, длительность.
- Код ошибки и её класс (ошибка БД / ошибка валидации / внешние данные) — чтобы по логам отличать «упала база» от «пользователь прислал мусор».
- Для worker: имя задачи, время начала/конца, длительность, результат (успех/ошибка/ретрай).

### 2.4. Корреляция запросов (request id)
- nginx генерирует уникальный request id для каждого входящего запроса и передаёт его в api через заголовок.
- api пишет этот id в **каждую** строку лога по этому запросу и возвращает его в ответе.
- Результат: по одной строке из access-лога nginx можно найти все связанные строки в логе api — видно всю цепочку «клиент → nginx → api → БД».

### 2.5. Гигиена
- Никогда не логировать: пароли, токены, jwt, cookie, содержимое .env. При необходимости логировать пользователя — только его id.
- Единая точка формирования лога ошибки в api: один общий обработчик ошибок Express, через который проходят все ошибки (сейчас, судя по коду, единого обработчика может не быть — это первое, что появит «понятность»).
- Необработанные исключения и отклонённые промисы (uncaughtException / unhandledRejection) — логировать с уровнем error и завершать процесс чисто: Docker поднимет контейнер заново, а в логе останется точная причина.

## 3. Уровень 2 — Централизованный сбор логов

Сейчас логи размазаны по контейнерам (`docker logs <контейнер>` по одному). Нужна одна точка, где видно всё.

### 3.1. Обязательный минимум (сделать сразу, бесплатно)
- Настроить ротацию логов Docker (ограничение размера и числа файлов для json-file драйвера). Без этого логи растут бесконечно и однажды **забивают диск** — а забитый диск валит Postgres. Это самая частая «внезапная» авария на маленьких VPS.

### 3.2. Основной вариант: Grafana Loki + Grafana (self-hosted, рядом со стеком)
- **Loki** — хранилище логов, собирает stdout всех контейнеров (через Promtail или Docker-драйвер loki).
- **Grafana** — один интерфейс: вкладка с логами (поиск по сервису, уровню, request id, тексту ошибки) + вкладка с дашбордами метрик.
- Всё добавляется вторым compose-файлом рядом с текущим стеком, менять приложение не нужно.
- Хранение: 14–30 дней достаточно на старте.

### 3.3. Запасные варианты
- **Быстрее и проще:** Dozzle (веб-интерфейс над docker logs всех контейнеров сразу). Даёт «видеть всё в одном окне», но без поиска по истории — можно поставить на первую неделю как временную меру.
- **Облачный вариант (минимум обслуживания):** Grafana Cloud (бесплатный тариф) или Better Stack — логи уходят наружу с сервера. Плюс: если VPS умер целиком, логи последних минут всё равно доступны и видна сама «смерть».

## 4. Уровень 3 — Healthcheck для всех сервисов

Цель healthcheck — отличать три состояния: «процесс жив», «жив и отвечает», «жив, но не работает». Сейчас есть healthcheck у api (curl на /health) и у db (pg_isready). Доводим до полной картины.

### 4.1. api
- Расширить существующий эндпоинт /health: кроме «процесс жив» проверять **реальную работоспособность** — выполнить тестовый запрос к БД (например, простейший SELECT 1) и вернуть обобщённый статус: ok (всё работает) или degraded (процесс жив, но БД недоступна).
- Healthcheck в compose оставить на лёгкий вариант «жив ли процесс», а «деградация БД» дополнительно отражать в метриках/логах, чтобы unhealthy из-за БД и unhealthy из-за мёртвого процесса различались.

### 4.2. worker (сейчас healthcheck нет — самый большой слепой зон)
- Worker — не HTTP-сервис, ему нужен **heartbeat**: worker периодически (например раз в 30 секунд) обновляет метку времени «я жив» (файл-таймстамп или запись в БД).
- Healthcheck контейнера проверяет свежесть этой метки: если worker не бился сердцем дольше пары минут — контейнер помечается unhealthy.
- Дополнительно worker логирует начало и конец каждой задачи — видно, «висит он или работает».

### 4.3. db
- pg_isready уже есть — оставить. Дополнительно следить за числом соединений и свободным местом (см. метрики).

### 4.4. nginx
- Добавить healthcheck, проверяющий локальный ответ (например, служебная страница статуса или проверка, что nginx отвечает на локальный порт и отдаёт 200/свою заглушку).
- Отдельно мониторить коды ответов наружу (см. метрики): всплеск 502 = упал api, 504 = api завис.

### 4.5. certbot
- Сам по себе он «жив», но смысл его работы — свежесть сертификатов. Мониторить **возраст/срок действия сертификата** снаружи (см. раздел 6), а не процесс certbot.

### 4.6. Порядок запуска
- Явно связать контейнеры через зависимость «стартуй, только когда зависимый здоров»: api стартует после db, nginx — после api. Иначе после перезапуска сервера api может стартовать раньше БД и падать в цикле, засоряя логи.

## 5. Уровень 4 — Метрики (Prometheus + Grafana, или Netdata для быстрого старта)

### 5.1. Что собираем и с какими порогами

| Что | Метрика | Порог внимания | Порог аварии |
|---|---|---|---|
| VPS | занято места на диске | 80 % | 90–95 % |
| VPS | свободная RAM, load average | RAM 80 % | RAM 90 %+ |
| Контейнеры | статус: running / unhealthy / перезапускался | любой рестарт без причины | unhealthy дольше 1–2 мин |
| nginx | доля ответов 5xx | > 1 % за 5 мин | > 5 % за 5 мин |
| nginx | время ответа | рост тренда | p95 > 2–3 c |
| api | rate ошибок уровня error в логах | всплеск относительно обычного | устойчивый всплеск 5+ мин |
| api | активные соединения с БД | > 70 % лимита | близко к лимиту |
| db | число соединений, размер баз, «медленные» запросы | тренд роста | лимит соединений |
| SSL | дней до истечения сертификата | < 14 | < 7 |
| worker | свежесть heartbeat, длительность задач | задачи дольше обычного | heartbeat молчит > 2–5 мин |

### 5.2. Инструменты — два пути
- **Классика:** Prometheus + node_exporter (хост) + cAdvisor (контейнеры) + Grafana для отрисовки. Гибко, стандарт индустрии, но ~4–5 контейнеров и заметный расход RAM.
- **Компромисс для одного VPS:** Netdata — один агент, ставится быстро, из коробки даёт метрики хоста, Docker-контейнеров и алерты; дашборд «что упало» получается почти без настройки. Можно начать с него, а Loki оставить только под логи.

## 6. Уровень 5 — Внешний мониторинг (обязательно!)

Внутренний мониторинг живёт на том же сервере, что и сайт. Если упал весь VPS или nginx — внутренние алерты **молчат вместе с сайтом**. Нужен проверяющий снаружи.

- Внешний сервис аптайма (Uptime Kuma на любом другом бесплатном VPS/дома, либо облачные UptimeRobot / Better Stack на бесплатном тарифе) проверяет каждые 1–5 минут:
    - https://zelenyeusy.ru — ожидаем ответ 200;
    - API через домен — ожидаем 200 от health-эндпоинта;
    - срок действия SSL-сертификата (алерт за 14 дней);
    - срок делегирования домена.
- Канал уведомлений тот же, что и для всего остального: Telegram.
- **Dead man's switch:** внешний монитор следит и за самим сервером мониторинга (например, пингует health-эндпоинт Grafana/Netdata). Если внутренний мониторинг умер — об этом тоже придёт сообщение.

## 7. Уровень 6 — Алерты: правила «что считать аварией»

### 7.1. Канал доставки
- **Telegram-бот** — мгновенно, бесплатно, с телефона. Создаётся один бот, все алерты в один чат/канал.
- Email — как дублирующий канал для критических (на случай, если Telegram ляжет).

### 7.2. Правила и приоритеты

| Приоритет | Условие | Что в сообщении |
|---|---|---|
| CRITICAL | контейнер unhealthy или перезапустился | имя сервиса, сколько раз, последние строки его лога |
| CRITICAL | сайт недоступен извне (внешний монитор) | что именно не отвечает, с какой минуты |
| CRITICAL | доля 5xx > 5 % в течение 5 минут | сервис-источник, топ ошибок из логов |
| CRITICAL | диск > 90 % | сколько осталось, кто больше всех занимает |
| WARNING | диск > 80 %, RAM > 85 % | текущие значения, тренд |
| WARNING | сертификат < 14 дней | дата истечения |
| WARNING | worker молчит > N минут или задача висит дольше обычного | имя задачи, время |
| WARNING | всплеск error-логов в api | счётчик за 5 минут, примеры сообщений |
| INFO | сайт снова доступен / проблема ушла (resolve) | время простоя |

### 7.3. Анти-спам (важно, иначе алерты начнут игнорировать)
- Группировка одинаковых алертов (одно сообщение, а не 50).
- Повтор одного и того же алерта не чаще, чем раз в N минут.
- Обязательное сообщение «проблема устранена» с длительностью простоя.
- **Текст-подсказка в каждом алерте** (мини-runbook): что посмотреть в первую очередь. Примеры формулировок: «api unhealthy → смотри последние строки лога api; если ошибки подключения к БД — проверь контейнер db и место на диске», «диск > 90 % → сначала очисти старые docker-образы, проверь pgdata и логи».

### 7.4. Где живут правила
- Правила на метрики — в алертинге Prometheus/Netdata (Alertmanager, если Prometheus).
- Правила на логи (всплеск error в Loki) — через Loki ruler или Grafana Alerts.
- Правила внешней доступности — во внешнем мониторе (раздел 6).
- Все пороги из таблицы в 5.1 зафиксировать как конфиг (файлом в репозитории), чтобы их можно было менять осознанно и видеть историю изменений.

## 8. Уровень 7 — Дашборд «что упало за 5 секунд»

Одна главная панель (Grafana или Netdata), сверху вниз:
1. **Строка статусов сервисов цветом:** nginx / api / worker / db / certbot / хост — зелёный/жёлтый/красный. Это и есть ответ на «сразу вижу, ГДЕ авария».
2. **Здоровье снаружи:** доступность zelenyeusy.ru из интернета, время ответа, дней до конца SSL.
3. **Ресурсы:** диск, RAM, load — с линиями порогов 80/90 %.
4. **Трафик и ошибки:** RPS, доля 5xx, счётчик error-логов по сервисам.
5. **Последние алерты** — лента сработавших правил.
6. Рядом — вкладка с логами (Loki) с сохранёнными фильтрами: «все error за последний час», «логи api по request id».

## 9. Порядок внедрения (по этапам, от самого ценного к тонкой настройке)

**Этап 0 — «скорая помощь», полдня–день.**
Ротация логов Docker (защита от забитого диска) + внешний аптайм-монитор с Telegram-уведомлениями + Telegram-бот.
*Результат: о любом падении сайта уже узнаю в Telegram, даже если сервер лежит целиком.*

**Этап 1 — понятные логи, день.**
Единый формат структурных логов в api и worker; уровни; стек и контекст у каждой ошибки; общий обработчик ошибок в api; request id от nginx через api; логирование жизненного цикла задач worker; вычистка секретов из логов.
*Результат: по логу понятно, что упало, в каком месте и в каком запросе.*

**Этап 2 — healthcheck, день.**
Расширить /health проверкой БД; добавить heartbeat- healthcheck воркеру; healthcheck для nginx; зависимости «стартуй после того, как зависимый здоров» в compose.
*Результат: контейнер, который «жив, но не работает», помечается unhealthy — это видно в docker и в мониторинге.*

**Этап 3 — централизация логов и метрик, 2–4 дня.**
Loki + Grafana (или Netdata + Loki) рядом со стеком; дашборд из раздела 8; правила алертов из раздела 7 (метрики + логи).
*Результат: одна панель, где цветом видно статус всех сервисов; история логов с поиском; алерты по порогам.*

**Этап 4 — по желанию, далее.**
Мониторинг медленных запросов Postgres, p95-времени ответа api, алерт на аномалии трафика, перенос части логов в облако, трейсинг.

**Как проверять каждый этап (не дожидаясь настоящей аварии):**
- остановить один контейнер → убедиться, что пришёл CRITICAL в Telegram с именем сервиса, и он красный на дашборде;
- заполнить диск тестовым файлом до порога → убедиться, что пришёл WARNING;
- положить БД (остановить контейнер db) → убедиться, что api показывает degraded и это видно и в логах, и в алерте;
- проверить, что «resolve»-сообщение приходит при восстановлении.

## 10. Итоговый критерий готовности (чек-лист приёмки)

- [ ] Останавливаю любой из сервисов (nginx, api, worker, db) — в течение ~1–2 минут в Telegram приходит алерт с именем упавшего сервиса.
- [ ] Открываю дашборд — вижу красным, какой именно сервис упал, без чтения логов.
- [ ] Открываю логи — нахожу ошибку с уровнем error: время, сервис, стек, request id, контекст запроса.
- [ ] Умею по request id связать строку nginx со строками api.
- [ ] Диск заполнен до 90 % → приходит алерт ДО того, как упадёт Postgres.
- [ ] Сертификату осталось < 14 дней → приходит алерт до истечения.
- [ ] Весь сервер выключен → внешний монитор присылает алерт (внутренние молчат — и это ок).
- [ ] Логи не содержат паролей/токенов и не растут бесконечно (ротация настроена).
- [ ] Каждый алерт содержит подсказку, что делать дальше.

## 11. Риски и примечания

- **Ресурсы VPS:** Loki + Grafana + Prometheus съедят заметную часть RAM маленького сервера. Если сервер слабый — начинать с Netdata + Loki, Prometheus отложить.
- **Секреты:** токен Telegram-бота и доступы к мониторингу хранить в .env на сервере (не коммитить), как и остальные секреты проекта.
- **Часовые пояса:** все логи и метрики в UTC; в интерфейсе Grafana можно отображать локальное время — главное, единообразие.
- **Не превратить мониторинг в шум:** лучше 8 полезных алертов, чем 80 раздражающих. Пороги из разделов 5 и 7 — стартовые, после пары недель «боевой эксплуатации» их стоит подкрутить по факту.
- **Runbook:** по мере эксплуатации дополнять подсказки в алертах реальными причинами прошлых аварий — со временем это станет самой ценной частью системы.
