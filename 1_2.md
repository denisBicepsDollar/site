- Замена `console.*` на логгер в: `server.js`, `errorHandler.js`, `worker/worker.js`, `bin/worker.js`, `reportService.js`, контроллерах, `db/**` (по списку из Части 0).
- `nginx/nginx.conf` — формат access-лога и проброс request id.

# ЧАСТЬ 1. УРОВЕНЬ 1 — Понятное логирование ошибок

## Шаг 1.0. Решения до начала (15 минут)
- [ ] Выбрать библиотеку структурных логов. Рекомендация: **pino** — быстрый, пишет JSON в stdout из коробки, есть встроенная сериализация ошибок и механизм «редакции» секретов. Альтернатива — winston (медленнее, больше настройки).
- [ ] Договориться о значениях уровней: число 50 = error, 40 = warn, 30 = info, 20 = debug (это внутренние уровни pino, они пригодятся при фильтрации в Loki на Уровне 2).
- [ ] Определить правило уровней для проекта (записать в README или в шапку `logger.js`):
    - `error` — работоспособность нарушена (упал запрос к БД, необработанная ошибка, 5xx);
    - `warn` — ожидаемая/обработанная проблема (404, ошибка валидации, невалидный токен, неудачная задача воркера с повтором);
    - `info` — старт/остановка, приём запроса, факт выполнения задачи;
    - `debug` — детали для расследования, в проде выключен.

## Шаг 1.1. Единая точка логгера (30–40 минут)
- [ ] Добавить pino в зависимости `back/server`.
- [ ] Создать `src/utils/logger.js` — единственный модуль, который создаёт логгер. Все остальные файлы импортируют его, а не создают свои инстансы.
- [ ] Внутри логгера задать:
    - базовое поле `service`: значение из переменной окружения `SERVICE_NAME` (в compose для api — `api`, для worker — `worker`; добавить переменную в `.env.example` и в два сервиса compose);
    - метку времени в UTC (стандартный формат ISO);
    - уровень из `LOG_LEVEL` (в проде по умолчанию `info`, в dev — `debug`);
    - сериализатор ошибок, чтобы объект ошибки превращался в поля `type / message / stack`;
    - механизм редакции секретов (pinoRedact): пути `req.headers.cookie`, `req.headers.authorization`, поля `password` — чтобы секреты физически не попадали в лог.
- [ ] Отдельно решить: никакой «красивой печати» (pino-pretty) в продакшене — только JSON. pretty допустим только локально в dev через отдельный флаг.

## Шаг 1.2. Замена console.* по всему коду (2–3 часа, механическая работа)
- [ ] Пройти по списку файлов из Части 0 (восемнадцать файлов), в каждом заменить `console.log` → `logger.info`, `console.error` → `logger.error` (или `warn` — по правилам уровней из Шага 1.0).
- [ ] В сообщениях оставить прежний смысл, но вынести переменные из строки текста в структурированные поля. Пример принципа: вместо строки «processReport failed id=5: …» — сообщение «processReport failed» плюс отдельные поля `reportId: 5`, `err: …`. Текст — короткая константа, данные — поля. Это главное условие, чтобы по логам потом можно было фильтровать.
- [ ] Особое внимание репозиториям БД (`rowRepo`, `shopRepo`, `tableRepo`, `reportsRepo`, клиенты): сейчас они логируют напрямую. Разделить: технические детали отладки → `debug`, реальные неудачи запросов → `warn`/`error` с кодом ошибки Postgres.
- [ ] Проверить, что после замены не осталось ни одного `console.` в `src` (поиск по проекту должен давать ноль результатов).

## Шаг 1.3. Сквозной request id (1–1,5 часа)
- [ ] **nginx:** включить использование встроенной переменной `$request_id` (генерируется nginx для каждого запроса автоматически). В каждом `proxy_pass`-location (`/api/` на публичном, `/admin/`, `/api/`, `/auth/` на админском) добавить проброс заголовка `X-Request-Id` со значением `$request_id` к api.
- [ ] **nginx:** описать собственный `log_format` для access-лога, включив в него `$request_id`, `$status`, `$request_time`, `$upstream_response_time` и переключить access-лог на этот формат.
- [ ] **api:** новый middleware (например `src/middleware/requestContext.js`), который: читает заголовок `X-Request-Id` (а если нет — генерирует `crypto.randomUUID()`); сохраняет id в контексте запроса; создаёт «дочерний» логгер запроса с полем `request_id`, чтобы ВСЕ строки лога внутри обработки запроса автоматически несли этот id; вешает на ответ заголовок `X-Request-Id` наружу (пригодится при разборе жалоб пользователя).
- [ ] **errorHandler:** брать request id из контекста запроса и писать в каждой ошибке.
- [ ] Проверка шага: сделать запрос к любому API-методу → в access-логе nginx и в логе api один и тот же id; заголовок `X-Request-Id` виден в ответе.

## Шаг 1.4. Access-лог самого api (40 минут)
- [ ] Добавить middleware access-лога (ставится последним перед errorHandler): на каждый завершённый запрос писать одну строку `info` с полями: метод, путь, статус, длительность в мс, request id.
- [ ] Уровень строки зависит от статуса: 5xx → `error`; 4xx → `warn`; 2xx/3xx → `info`.
- [ ] Не логировать (или логировать в debug) обращения к `/health` — иначе healthcheck Docker засорит лог несколькими строками каждые 5 секунд.

## Шаг 1.5. Обработчик ошибок: классификация и контекст (1 час)
- [ ] В `errorHandler.js` перейти на логгер запроса (из Шага 1.3) и логировать:
    - для `ApiError` → уровень `warn` (это ожидаемые ошибки: «нет такого ресурса», «не авторизован»), поля: статус, сообщение, request id;
    - для ошибок валидации и токенов → `warn`;
    - для всего остального → `error` с полным стеком и типом ошибки.
      Смысл: настоящий авария-сигнал (5xx) не должен теряться в потоке от «пользователь ввёл неверный пароль».
- [ ] Убедиться, что клиенту по-прежнему уходит чистый ответ без стека (в проде), а стек остаётся только в логе.

## Шаг 1.6. Логи жизненного цикла процессов (1 час)
- [ ] В `server.js` и `bin/worker.js` добавить обработчики:
    - `uncaughtException` → `logger.fatal` со стеком и завершением процесса (Docker поднимет контейнер по `restart: unless-stopped`, причина останется в логе);
    - `unhandledRejection` → `logger.error` с причиной (и по решению — тоже завершать процесс; для воркера завершать обязательно, чтобы «подвисший» промис не оставил мёртвого на вид живого воркера);
    - `SIGTERM` → `logger.info` «получен SIGTERM, останавливаюсь», корректно закрыть HTTP-сервер / текущую задачу воркера и выйти. Теперь при каждом деплое (`deploy.sh` пересоздаёт контейнеры) в логах будет видна чистая остановка, а не обрыв.
- [ ] Стартовые строки: api логирует «стартовал» с портом и окружением; worker — «запущен» с интервалом опроса.

## Шаг 1.7. Логи задач воркера (1–1,5 часа)
- [ ] В цикле воркера и `reportService` логировать три события по каждой задаче (уровень `info`, поля — структурированные):
    - начало: `reportId`, таблица;
    - конец: `reportId`, длительность в мс, результат (успех / повтор / ошибка);
    - неудача: уровень `warn` при первой неудаче (если в сервисе есть механика повторов) и `error`, если неудачи идут подряд (счётчик в памяти воркера: например, 3+ подряд → `error` со суммарным сообщением).
- [ ] Смысл: по логам должно быть видно «воркер работает, но задача X трижды упала» и «воркер жив, задач нет» — это два разных состояния, и выглядеть в логе они должны по-разному.
- [ ] (Задел на Уровень 3.) Параллельно воркер может обновлять метку времени «я жив» — файл в смонтированном томе `./storage`. Пока просто отметить это как следующий шаг, к healthcheck воркера.

## Шаг 1.8. Аудит секретов (30 минут)
- [ ] Прочитать глазами все места, где логируются запросы/пользователи: не должны попадать пароль, jwt, cookie, содержимое `.env`. Пользователь — только по id.
- [ ] Убедиться, что редакция секретов из Шага 1.1 включена и покрывает заголовки.
- [ ] Запомнить правило на будущее: новый лог — сначала вопрос «может ли это поле содержать секрет?».

## Шаг 1.9. Приёмка Уровня 1 (30 минут)
Проверить на проде (или стенде с тем же compose):
- [ ] Запрос несуществующего маршрута → в логе `warn` со статусом 404 и request id, БЕЗ стека на весь экран.
- [ ] Остановить контейнер db, дёрнуть API-метод, читающий данные → `error` со стеком и кодом ошибки БД; запустить db обратно.
- [ ] Создать задачу отчёта → в логах worker видны начало, конец и длительность задачи.
- [ ] Любая случайная строка лога парсится как JSON; поля `time`, `level`, `service` на месте.
- [ ] Поиск по репозиторию `console.` даёт ноль результатов.
- [ ] В логах нет паролей/токенов (проверить логин в админку).

# ЧАСТЬ 2. УРОВЕНЬ 2 — Централизованный сбор логов

## Шаг 2.0. Ротация логов Docker — сделать ДО всего остального (30 минут)
Это защита от самой частой аварии на маленьком VPS (логи съели диск → упал Postgres).
- [ ] Выбрать способ: (а) секция `logging` с драйвером `json-file` в каждом сервисе `docker-compose.yml`, либо (б) один раз задать дефолт в `daemon.json` на хосте. Рекомендация: (а) — настройки лежат в репозитории и видны в коде.
- [ ] Лимиты: размер одного файла ~10 МБ, файлов ~3 (то есть максимум ~30 МБ на контейнер). Для nginx можно отдельные лимиты (у него access-лог болтливее).
- [ ] Важно: лимиты применяются только при пересоздании контейнера — после правки compose обязательно полный пересоздающий `up -d`, а не просто restart.
- [ ] Проверка: найти файлы логов контейнеров на хосте (`/var/lib/docker/containers/*/*-json.log`), убедиться, что у пересозданных контейнеров стоит лимит (в метаданных контейнера), и старые гигантские логи не продолжают расти.

## Шаг 2.1. Решения по стеку сбора (15 минут)
- [ ] Схема: **Loki** (хранилище) + **Promtail** (сборщик) + **Grafana** (интерфейс: и логи, и будущие метрики/дашборд).
- [ ] Способ сбора: Promtail с автообнаружением Docker-контейнеров (docker service discovery). Причина против альтернативы (logging-драйвер loki): драйвер надо прописывать в каждый сервис, а Promtail подхватывает всё автоматически и переживает пересоздания контейнеров.
- [ ] Проверить ресурсы VPS: `free -h`. Ориентир по расходу: Grafana ~200–300 МБ RAM, Loki ~150–300 МБ, Promtail ~50 МБ. Если свободно меньше ~1 ГБ — сначала расширить VPS или начать только с Loki без Grafana (искать запросами через web-интерфейс Loki), а Grafana добавить позже.
- [ ] Хранение логов: 14 дней на старте (потом отрегулировать по размеру диска).

## Шаг 2.2. Файлы мониторингового стека (1–2 часа)
- [ ] Создать отдельный compose-файл мониторинга (например `docker-compose.monitoring.yml`), НЕ смешивать с продовым: прод перезапускается каждым деплоем через `deploy.sh`, мониторинг должен жить независимо.
- [ ] Сети: подключить контейнеры мониторинга к существующей внешней сети `app-net` (Grafana и Promtail будут ходить по именам сервисов) либо создать свою отдельную сеть — достаточно своей, если Promtail читает логи Docker напрямую, а наружу Grafану expose'ить портом.
- [ ] Тома: данные Loki и Grafana — в named volumes или в каталоге `./monitoring/data/...` на хосте; убедиться, что каталог не попадает в Git (при необходимости добавить в `.gitignore`).
- [ ] Конфиг Loki (файл в `monitoring/`): файловая система как хранилище, период хранения 14 дней, включён компактор для удаления старых данных. Это критично: без retention Loki будет расти бесконечно — та же проблема, что и логи Docker без ротации.
- [ ] Конфиг Promtail (файл в `monitoring/`): docker service discovery; смонтировать сокет Docker (read-only) и каталог контейнерных логов хоста (read-only); файл позиций (`positions.yaml`) — в том, чтобы после рестарта не перечитывать всё заново и не плодить дубликаты.
- [ ] Пароли: сразу задать пароль администратора Grafana через переменные окружения (в `.env` на сервере, не в Git), сменить дефолтный admin/admin при первом входе.

## Шаг 2.3. Разметка логов (labels) (1 час)
- [ ] В Promtail настроить pipeline: из JSON-строк pino доставать `service`, `level` и делать их лейблами; имя Docker-контейнера — тоже лейбл (для nginx, у которого логи не JSON).
- [ ] Правило кардинальности: лейблами делают ТОЛЬКО малочисленные поля (`service`: api/worker/nginx/db — единицы значений). Поля с уникальными значениями (`request_id`, `reportId`) — НЕ лейблы, они ищутся полнотекстовым фильтром или как structured metadata.
- [ ] Проверка: в Grafana Explorer запрос `{service="api"}` возвращает поток логов api; `{service="nginx"}` — access-лог nginx.

## Шаг 2.4. nginx-логи в Loki (30 минут)
- [ ] У официального образа nginx access/error лог уже идёт в stdout (симлинки встроены) — значит, Promtail подхватит их автоматически. Проверить, что строки nginx видны в Loki с лейблом контейнера `nginx`.
- [ ] После того как на Уровне 1 в nginx появится кастомный `log_format` с `$request_id`, проверить, что строки в Loki содержат id и поиск по нему работает: фильтр по значению request id находит и строку nginx, и связанные строки api.

## Шаг 2.5. Grafana: источник и сохранённые запросы (1 час)
- [ ] Добавить источник данных Loki (внутренний адрес сервиса Loki внутри compose-сети, порт по умолчанию 3100).
- [ ] Сохранить в Explorer готовые запросы (кнопка «Add to dashboard» / starred queries):
    - «Все ошибки за час»: `{service=~"api|worker"} | level >= 40` (level 40+ = warn и error);
    - «Логи одного запроса»: `{service=~"nginx|api"} | request_id="..."` — подставлять id при разборе инцидента;
    - «Жизнь воркера»: `{service="worker"}` — видно начало/конец задач;
    - «Ошибки nginx»: `{service="nginx"} |~ " 5[0-9][0-9] "` — строки 5xx из access-лога.
- [ ] Собрать мини-дашборд «Логи» из двух панелей: верхняя — поток error/warn всех сервисов, нижняя — таблица последних ошибок. Полный дашборд метрик — это Уровень 4, пока не нужен.

## Шаг 2.6. Безопасность доступа к Grafana (20 минут)

Два допустимых варианта: (а) доступ только по SSH-туннелю с локальной машины (порт вообще не публикуется на 0.0.0.0); (б) публикация на поддомене через существующий nginx с basic-auth (по образцу уже настроенной защиты админки). Рекомендация: (а) — проще и безопаснее.
- [ ] Если выбрали (а): убедиться, что в compose порт Grafана проброшен только на localhost-интерфейс хоста, а не на все интерфейсы.

## Шаг 2.7. Живучесть мониторинга (30 минут)
- [ ] Контейнерам Loki/Grafana/Promtail выставить `restart: unless-stopped` и healthcheck (Grafана отдаёт отдельный health-эндпоинт, Loki — свой; Promtail проверяется готовностью файла позиций или просто живостью процесса).
- [ ] Задел на раздел 6 основного плана: внешний аптайм-монитор позже добавит проверку доступности Grafаны — это и будет «контроль за самим контролёром».

- [ ] В `.env.example` добавить новые переменные (пароль Grafana, версии образов при желании).

# КРИТЕРИИ ГОТОВНОСТИ (сверка с исходной задачей)
- «Понятно, что именно падало» = в каждой ошибке есть: имя сервиса, уровень, стек, request id, статус; авария (5xx) отличается в логе от пользовательской ошибки (4xx). → Шаги 1.2–1.5, приёмка 1.9.
- «Падение сервиса видно в логах/мониторинге» = логи всех контейнеров в одном интерфейсе с фильтром по сервису и уровню; история переживает перезапуски; место под логи ограничено ротацией и retention. → Шаги 2.0, 2.2–2.5, приёмка 2.9.

# ГРАБЛИ (типовые ошибки на этих двух уровнях)
1. **pino-pretty в проде** → логи перестают быть JSON, Loki не сможет парсить поля. Pretty — только локально.
2. **Ротация Docker без пересоздания контейнеров** → кажется, что настроено, а лимита нет. Только `up -d --force-recreate` (или полный `down/up`) применит лимиты.
3. **`request_id` сделан лейблом Loki** → взрыв кардинальности, Loki замедляется и раздувается. Label — только `service`/`level`/`container`.
4. **Loki без retention и компактора** → через месяц Loki сам забьёт диск. Сразу настроить 14 дней.
5. **Grafана с портом на 0.0.0.0 и паролем admin/admin** → первый же сканер найдёт её. Порт на localhost + SSH-туннель.
6. **Заменены не все console.*** → половина логов JSON, половина текстом; в Loki текстовые строки ищутся хуже. Контроль: grep по проекту = 0.
7. **Мониторинг в общем docker-compose.yml** → каждый деплой сайта перезапускает Loki/Grafану, история «мигает». Отдельный compose-файл.
8. **Логирование тела запроса целиком** → рано или поздно в лог утечёт пароль или персональные данные. Логируем только метод, путь, статус, id.
