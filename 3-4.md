# ЧАСТЬ А. МАСТ ХЕВ — уведомляющий контур (полдня работы)

## М1. Канал доставки — Telegram-бот (30 минут)
- [ ] Создать бота через BotFather, получить токен.
- [ ] Завести приватный чат (или канал) «Алерты zelenyeusy», добавить бота.
- [ ] Узнать id чата (написать в чат и посмотреть id через API бота).
- [ ] Токен и id чата — в `.env` на сервере (в `.env.example` добавить имена переменных без значений).
- [ ] Отправить тестовое сообщение — убедиться, что доходит.
- [ ] Правило на будущее: все алерты всей системы идут в этот один чат. Ничего не настраиваем в обход него.

## М2. Внешний мониторинг — «глаза снаружи» (1 час)
Это единственный слой, который переживает смерть всего сервера. Ставится в облаке, не на вашем VPS.
- [ ] Зарегистрироваться в облачном сервисе аптайма (UptimeRobot или Better Stack, бесплатного тарифа достаточно).
- [ ] Создать монитор №1 — «Магазин»: URL `https://zelenyeusy.ru`, ожидаемый ответ 200, интервал 1–5 минут.
- [ ] Создать монитор №2 — «API через nginx»: URL публичного метода, например `GET https://zelenyeusy.ru/api/products`, ожидаем 200.
  Важный нюанс (проверено по вашему nginx.conf): health-эндпоинт api НЕ проксируется наружу на публичном домене — nginx отдаёт наружу только `/api/`. Поэтому внешний монитор смотрит на реальный публичный метод — это даже честнее: проверяется вся цепочка «интернет → nginx → api → БД».
- [ ] Создать монитор №3 — «SSL-сертификат»: тип проверки «SSL/срок действия», алерт за 14 дней до истечения.
- [ ] (Опционально) монитор №4 — админ-домен. Учесть, что статика админки закрыта basic-auth, поэтому без пароля она отвечает 401 — монитор надо настраивать на ожидание 401 как «нормы» либо не делать вовсе.
- [ ] Канал уведомлений всех мониторов — Telegram (в UptimeRobot это «Alert Contact» типа Telegram, привязывается к боту из М1).
- [ ] Настройки, чтобы не будили зря: алерт только после 2 подряд неудачных проверок; уведомление «сайт снова поднят» обязательно; интервал проверок не чаще 1 раза в минуту.
- [ ] Проверить e-mail-дубль: пусть критические падения приходят и письмом — резервный канал на случай, если ляжет сам Telegram.

## М3. Внутренний сторож — cron-задача на сервере (1,5–2 часа)
Пока полноценных метрик и Alertmanager нет, аварию внутри сервера ловит простой периодический скрипт. Это осознанное временное решение (переезд на Prometheus+Alertmanager — в части Б).
- [ ] Создать на сервере cron-задачу с периодом раз в 1–2 минуты, которая проверяет:
  1. **Статусы healthcheck всех контейнеров** (`docker ps` в машиночитаемом виде): любой контейнер в статусе unhealthy или exited → алерт. Список проверяемых зафиксировать явно: nginx, api, worker, db — чтобы «потерянный» контейнер (упал и исчез из списка) тоже считался аварией, а не тишиной.
  2. **Факты рестартов**: сравнить счётчик перезапусков контейнера с прошлой проверкой — вырос → алерт (это ловит «падает-поднимается» циклы, когда между проверками контейнер успел стать healthy снова).
  3. **Место на диске**: занято > 80 % → warning, > 90 % → critical.
  4. **Свободная RAM**: < 15 % → warning.
- [ ] Формат сообщения: имя сервиса + что случилось + одна строка подсказки что делать. Примеры подсказок: «api unhealthy → docker logs api, чаще всего это БД или место на диске», «диск > 90 % → сначала docker image prune и старые логи, потом смотреть pgdata».
- [ ] Анти-спам: об одной и той же проблеме — не чаще одного сообщения в 15 минут; при исчезновении проблемы — сообщение «проблема ушла» с длительностью.
- [ ] Лог своих проверок и отправок скрипт пишет в файл в stdout → он попадает в Loki (Уровень 2) → всегда видно, «сторож молчал потому, что всё хорошо, или потому, что сам сломался».
- [ ] Отдельно убедиться, что cron переживёт перезагрузку сервера (системный cron/timer, а не процесс «запущенный руками по ssh»).

## М4. Приёмка маст хева (30 минут) — не пропускаать
- [ ] Остановить контейнер api → в течение 1–2 минут в Telegram пришло сообщение с именем сервиса. Запустить обратно → пришло «проблема ушла».
- [ ] Остановить контейнер worker → то же самое (проверяет и heartbeat/healthcheck из Уровня 3, и сторожа).
- [ ] Имитировать отказ «всего сервера» настолько, насколько можно на боевом: временно остановить ВСЕ контейнеры стоп-командой → алерт от внешнего монитора (М2) пришёл, хотя внутренний сторож молчал. Поднять всё обратно.
- [ ] Записать в заметки фактическое время «остановка → сообщение» — это и есть ваш текущий MTTD (время обнаружения).
- [ ] Убедиться, что за сутки тестов не было ложных срабатываний; если были — подкрутить пороги/ретраи.

**После М1–М4 исходная задача «если что-то произошло — alert придёт» закрыта полностью.** Всё остальное — улучшения: раньше, точнее, нагляднее.

# ЧАСТЬ Б. МОЖНО ПОТОМ — всё остальное из несделанного

Сгруппировано по тому, **какую боль убирает** каждый блок. Делать по очереди сверху вниз, не перепрыгивая.

## Б1. Алерты на логи через Grafana (2–3 часа) — «узнавать раньше, чем упадёт»
- [ ] Правило в Grafana/Loki: всплеск error-логов api или worker выше обычного уровня за 5 минут → уведомление в Telegram-чат из М1.
- [ ] Правило: доля 5xx в access-логе nginx > 5 % за 5 минут → алерт (логи уже содержат статус и request id после Уровней 1–2).
- [ ] Смысл блока: это алерты «по симптомам» — они срабатывают, когда сервис ещё формально жив, но уже плохо работает (например, каждая третья ошибка БД, но healthcheck пока зелёный).
- [ ] Обязательно с анти-спамом (группировка, повтор раз в N минут), иначе замолчит сам себя.

## Б2. Метрики: хост и контейнеры (полдня) — «история и графики»
- [ ] node_exporter + cAdvisor в мониторинговый compose (по `MONITORING_ACTIONS_LEVEL3_4.md`, шаги 4.2–4.4), retention с лимитом.
- [ ] Дашборд «Что упало за 5 секунд» из раздела 8 плана: строка статусов сервисов, диск/RAM с пороговыми линиями, 5xx из Loki рядом.
- [ ] Альтернатива при желании упростить: Netdata одним агентом вместо связки exporters.
- [ ] Смысл блока: сторож из М3 отвечает «что сломалось сейчас», метрики отвечают «что происходило до того» — тренды диска, памяти, рестартов. Без истории вы каждый раз расследуете аварию с нуля.

## Б3. Метрики PostgreSQL (полдня)
- [ ] postgres_exporter под отдельным пользователем только для мониторинга (шаг 4.5 из документа уровней 3–4).
- [ ] Приоритет: число соединений относительно суммарного лимита трёх пулов api (около 30), размеры баз, тренд роста.
- [ ] Смысл: единственная метрика, которая предупредит об аварии ЗА дни — неуклонный рост размера базы или соединений.

## Б4. Переезд алертов со сторожа на нормальный алертинг (1 день)
- [ ] Когда появятся метрики (Б2): перенести проверки диска/RAM/контейнеров из cron-сторожа в Alertmanager или Grafana Alerts — с группировкой, приоритетами CRITICAL/WARNING, тишиной на время работ.
- [ ] Сторож из М3 при этом НЕ удаляется: остаётся как «последняя линия» — проверка, что сам мониторинг жив (а living-проверка у Prometheus всегда одна — а вдруг сломался он).
- [ ] Пополнить подсказки-ранбуки в алертах реальными причинами уже пережитых аварий.

## Б5. Dead man's switch — контроль за контролёром (1–2 часа)
- [ ] Внешний монитор (из М2) получает ещё одну проверку: URL, который отвечает только живой внутренний мониторинг (health-эндпоинт Grafana или Loki, доступ к которому даёт nginx с ограничением).
- [ ] Смысл: ловит ситуацию «сторож/метрики умерли час назад, и всё это время вы думали, что всё под контролем».

## Б6. Углубления — по мере роста проекта (когда-нибудь)
- [ ] Метрики самого api (prom-client): p95 времени ответа, очередь отчётов воркера, состояние пулов БД. Пора, когда из логов станет не хватать скорости анализа.
- [ ] Мониторинг медленных запросов PostgreSQL (pg_stat_statements): пора, когда жалобы «медленно» станут регулярными.
- [ ] Трейсинг (распределённые трассы nginx → api → БД): пора, когда request id в логах перестанет хватать для разбора сложных случаев.
- [ ] Бюджеты ошибок/SLO, аномалии трафика: пора при заметном трафике, не раньше.
- [ ] Если появятся бэкапы (их стоит иметь!): алерт «бэкап не сделался / не восстановился» — по опыту, самый недооценённый мониторинг в маленьких проектах.

## Как понять, что пора переходить от маст хева к следующему блоку (триггеры)
| Ситуация | Что делать |
|---|---|
| Сторож М3 прислал алерт, а вы не поняли, НАСКОЛЬКО всё плохо (нет истории) | Б2 — метрики |
| Узнаёте об аварии позже, чем хотелось (симптомы были в логах раньше) | Б1 — алерты на логи |
| Появился страх «а вдруг мониторинг сам сломался» | Б5 — dead man's switch |
| Алертов стало много, они дублируют друг друга | Б4 — группировка и приоритеты в Alertmanager |
| База растёт, соединения под лимитом | Б3 — postgres_exporter |
| Меняется архитектура (новые сервисы) | дописывать их в сторож М3 сразу при деплое |
